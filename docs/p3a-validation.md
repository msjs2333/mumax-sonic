# P3a：OVF 发布清单的后台跟随

P3a 交付实时链路的第一步：后台跟随已完整发布的 OVF 清单，沿用 P2d 的哈希、材料掩膜、XYZ 和物理时间契约。此阶段不直接操控 MuMax3/MuMax+ 求解器，不运行 GPU 仿真。

## 使用

```powershell
python launch.py --follow local/live-demo/live.json --recipe activity --aggregation adaptive --source-budget 8
python scripts/publish_live_demo.py local/live-demo --frames 60 --interval-s 0.1
```

两个终端运行，可先启动窗口。发布目录必须为空；再次演示请换目录。发布器每步生成 17×17 的完整 XYZ 解析旋转场，物理步长为 50 ps，默认墙钟发布间隔 0.1 s，两种时间不混用。新帧写完且验证后，清单通过同目录临时文件与原子替换发布。来源明确标记 synthetic，不代表真实求解器。

`--follow` 是独立 GUI 输入，不能与回放、演示、离线检查或设备 smoke 参数混用。窗口配方和频带设置改变后重启跟随器；实时源由发布端推进，跳转和播放倍速不会改它的物理时间。音频仍需主动开启。

## 数据与质量

`LiveFollower` 的守护线程执行文件读取、完整性校验和物理观察。Tk 只读取简短快照，不读取 OVF 或执行观察器；自适应聚合沿用后台任务，物理贡献与 ROI 分开。快照携带状态、实际 FieldView、物理帧更新次数、读取与观察耗时、新帧年龄及错误。

等待清单或首个完整观察时保持静音；activity 首帧、band 历史不足仍按原观察器预热。物理帧来源标记 live，同时保留清单原始来源和哈希证据；live 仅表示接入方式，不代表数据来自真实仿真。

默认墙钟超时 2 s（`--live-stale-s`）：年龄从发现新发布到当前计算，包含读取和观察耗时，重复发布同一物理帧不刷新。即使后台阻塞，快照读取也能判定超时。失效和损坏状态保留最后画面及物理时间，但声音静音；迟到文件和修复清单会重试恢复。文件修改时间只用于发现发布，不能充当物理仿真时间。

一个 segment 的清单只允许追加历史，不允许截断、回退或改写已发布帧的内容/时间/单位/材料掩膜。新的 segment 可重置时间。记录指纹不绑定整个清单哈希，追加清单不会误判历史帧改变。原文件在发布后须保持不可变。

每次对最新完整帧计算观察；活动仍使用清单中真正相邻的源帧，频带使用完整尾部历史。界面未展示的中间帧以 `skipped_observation_frames` 统计，区别于源文件缺帧；不会把最新两次 GUI 更新当作相邻物理采样。该模式不能保证听到两次观察之间的瞬时事件。

## 验证与边界

完整回归、并发合成发布、真实 Tk 等待/有效/超时/恢复流程均检查；具体本轮结果记录于下方。测试包含半写清单、迟到帧重试、哈希错误、历史改写/截断、后台阻塞期间超时、关闭后不再发布、物理时间与墙钟时间分离。

P3a 每次发布重新校验整个清单；继承最多 4096 帧及现有读取容量限制，不是无限流。旧帧只读哈希验证和发布端自校验的成本随历史增长，尚不满足低开销生产级实时承诺。固定回放和演示的物理观察仍按原路径；本批后台化针对 live 输入。

本批端到端使用 CPU 合成发布和无音频 Tk 窗口，未声称实际设备实时延迟、耳机听辨、真实求解器实时性能或低于 5% 监测开销。历史 P2 的真实数据/设备检查不可当成本阶段在线求解器验收。

下一步 P3b：缓存已验证不可变帧、按物理窗口增量读取，明确更长运行的保留策略；加入 MuMax3 完整输出到原子清单的发布桥接和成对开销基准。MuMax+ 直接采样在独立适配中验证，继续保留其实体/序参量语义。


本轮结果：`python -m pytest -q -rs` → **200 passed，无跳过**；`git diff --check` 通过。真实 Tk 窗口跟随 CPU 发布端 20 帧、50 ps 物理步长，观察到 waiting/current/stale，最终物理时间 0.95 ns，最多 8 个声音候选，所有 stale 样本均静音，关闭状态 closed。该检查未开启音频设备；源数据为 synthetic。默认超时以外的 QA 使用 1 s 超时，最新一次读取/观察耗时约 498 ms，说明全清单复验成本确实需要下一阶段优化。窗口截图与命令行帮助检查通过，本地原始 QA 报告和临时发布文件不提交。
