# P3d：接入等待与读取开销优化

2026-09-10。本批以 CDW 1500×500 活动模式的持续输入长尾为目标，不修改物理采样时间或拓扑/频带定义。

## 已实现

- Binary 4/8 桥接只读取 OVF 头部、校验字节、载荷长度和结束标记，不解码整场磁化；实际消费者仍完整读取 XYZ。保持原有小端支持范围，文本 OVF 回退原解码器。
- 桥接不再每次发布调用 `fsync`；文件关闭后原子发布。Windows 短暂替换占用在一次 poll 内最多尝试三次、总等待约 30 ms，仍占用则显示 waiting，后续 poll 继续，不增加内容哈希。掉电持久性不是实时只读清单的契约。
- 默认桥接匹配 `m[0-9]*.ovf`，排除 `m_initial.ovf` 等快照；显式自定义模式仍可用。桥接 CLI 与跟随器默认轮询间隔均为 50 ms。
- ROI-only 请求由事件唤醒，复用最近成功读取的物理窗口；新清单优先检查，不通过鼠标移动刷新数据年龄。无效/过期数据不会由旧 ROI 结果恢复为有效。
- 相同帧对、相同对齐分块的前景活动只计算一次。ROI 在块内移动仍会改变听觉权重；跨块、新帧、阶段或几何变化重新计算。缓存保留一份局部结果，无逐帧审计。
- 已压缩的关注区贡献只有数百项，直接在当前 UI tick 聚合，免去额外后台往返；全场大贡献集仍走后台。修复默认关注中心误传三维坐标的问题。
- `last_job` 保存最近一个任务的序号、类型、起止时间和分段耗时；生产端不保存无界日志。基准脚本收集记录并输出最慢的 12 个任务，以及观察完成到控制生效的剩余等待。

## 读缓冲区问题与定位证据

第一轮优化后仍出现约 4.53 秒任务，其中 `read_validate` 约 4.50 秒，观察约 29 ms。该计时把文件访问、掩膜解析、解码及帧构造合并在读取阶段，不能直接断言全部是磁盘硬件耗时。

进一步发现读取约 750128 字节的掩膜时，旧 `_bounded_bytes` 调用 `read(256 MiB + 1)`，在 Windows 为小文件产生了按巨大上限读取的额外成本。独立五次中位：旧路径 **87.34 ms**，按实际文件大小读取 **0.127 ms**。这能解释显著固定开销，但不是对该次 4.50 秒内部每一毫秒的归因。

现改为检查已打开文件的实际大小后仅申请相应读取量；OVF 的 `read(64 MiB + 1)` 同样去除。二进制载荷直接以 buffer+offset 解码，免除整段字节切片复制；Binary 8 可共享不可写原始缓冲区，发布 FieldFrame 时仍隔离成只读数据。单位、物理时间、形状、半写和内存上限检查保留。

相同真实两帧桥接的探测/发布耗时三次为 7.55、8.83、4.80 ms，中位 **7.55 ms**，之前完整解码约 **75.37 ms**。两次测量均不包含稳定轮询等待，文件缓存状态未清空。

另将相同连续帧复制到本地工作盘进行了 80 秒存储路径对照，在修复巨大读缓冲区之前未复现多秒任务，但正常读取仍约百毫秒；因此不能仅把慢速归咎于备份盘。最终对比继续使用原备份路径，不把迁移存储当作软件优化成绩。

| --- | ---: | ---: |
| 小圈静止 | 352 ms | 95 / 126 ms |
| 大圈静止 | 560 ms | 304 / 336 ms |

**严格的 100 ms 应用端 p95 目标仍未全面通过**。大圈成本已主要转到物理观察本身；扩大关注范围并非免费。后续需按测量决定观察算法/分块优化或较低更新率，不能悄悄降低物理空间/时间采样质量。

## 复现与新鲜度

```powershell

```

同条件延迟验收仍使用 2 秒 stale。对于约 1.4 秒/帧、可能成批到达的实际源，可显式采用 `python launch.py --follow path/to/live.json --recipe activity --focus-compute --aggregation adaptive --source-budget 8 --live-stale-s 4`。4 秒是有依据的用户配置起点，不是自动推断，不改变数据年龄，也不算作延迟提速。

数值为本机短时证据；存档清单发布测试不包含求解器写文件、桥接等待、设备缓冲和听觉平滑完成。没有运行本批的真实 GPU 成对仿真或人工声学延迟实验。
